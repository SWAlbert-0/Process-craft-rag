# 开发计划与风险

> 计划基线：2026-11-18。采用双周迭代，最终交付窗口为 2027 年 6 月。中期报告安排在下学期开学后的第 1—3 周。核心功能应尽早完成，后续迭代根据评估结果灵活用于优化、完善和验收，不为填满周期而增加范围或拖延交付。

## 1. 实施原则

- 先打通最小端到端链路，再补齐文档管理、会话产品和评估能力。
- 每轮迭代都有可运行产物、验证证据和复盘结论；未完成项不得用“代码已写”代替验收。
- 优先使用授权的真实文本型 PDF 和固定测试题，不用纯演示文本代替联调。
- 核心模块通过接口解耦，模型替换不改业务流程；最终验收必须使用真实模型和真实索引。
- 不把“API 能调用”视为完成，必须覆盖检索诊断、引用核查、证据不足和异常反馈。
- 迭代内容可根据难度和实测结果调整：阻塞核心质量的问题优先，非必要增强让位；范围变化不得静默发生。
- 若提前达到发布条件，后续周期只进行有证据支持的微调、稳定性完善、文档与验收准备，不刻意扩张功能。

## 2. 文档评估与计划改进点

### 2.1 当前成熟度

现有文档已经形成较完整的设计基线：需求范围明确，P0/P1 有区分，架构与数据模型基本对应，检索链路包含稠密召回、BM25、RRF、重排序和引用白名单，测试方案同时覆盖软件正确性与人工评估，安全边界也明确要求人工审核。

主要不足在执行层面：需要把设计转化为有日期、有需求映射、有准入/准出条件的双周迭代，并把中期检查与最终交付区分。计划将核心链路、产品闭环和首版质量基线优先安排在寒假前后；中期后主要依据真实评估结果改进，而不是平均分配功能到所有周期。

### 2.2 开发前需关闭的设计缺口

| 缺口 | 影响 | 处理要求 | 关闭时点 |
| --- | --- | --- | --- |

## 3. 排期约定与阶段目标

- 每轮迭代为两周。I1 周期为 2026-11-09—11-22，后续按连续双周安排；遇到寒假和开学日期变化，可调整轮内工作量，但不随意改变中期和最终交付窗口。
- 下学期开学后的前三周暂映射到 I8—I9；实际校历不同则平移中期材料任务，中期报告仍须在开学第三周结束前完成。
- 最终交付安排在 2027 年 6 月，I16 用于最终验收和交付；6 月 21—30 日仅作为交付缓冲，不安排新功能。
- 角色按前端、后端、RAG、测试/评估、运维划分。人员可兼任，但每项任务启动时必须落实到具体负责人。
- P0 优先于 P1；OCR、复杂表格结构还原、多租户、业务系统集成和机床控制不属于默认交付范围。只有 P0 已达标且评估证明确有价值时，才可评审可选增强。

## 5. 关键迭代验收要求

### I1：核心链路验证

**目标**：用一份授权、可提取文本的真实 PDF 跑通“上传/导入 → 解析分块 → 双路索引 → 混合召回 → 重排序 → 大模型生成 → 引用查看”的最薄闭环。

**两周安排**

- 前 2 个工作日：确认样例 PDF、指令模板、模型与合规；冻结首版 API/数据约定；决策多文档索引组织方案；初始化项目。
- 第一周剩余时间：完成数据库迁移、PDF 预检、页文本、清洗分块、确定性 ID、嵌入及 Qdrant/BM25 构建。
- 第二周前半段：完成双路召回、RRF、重排序、上下文构建、LLM、结构与引用校验及非流式消息 API。
- 第二周后半段：完成最小页面、Compose 联调、自动化测试、真实样例验收和复盘。

**范围边界**

本轮建立文档、索引版本、分块、任务、单轮会话/消息和引用模型，以及最小状态展示。完整登录权限、多轮会话、SSE、重建/删除管理、批量评估和 OCR 不在本轮，但保留在后续对应迭代中。

**准出条件**

1. 新环境按说明可启动，数据库可迁移，仓库无真实密钥和本机绝对路径。
2. 真实 PDF 达到 `ready`；页码、块数和原文可抽查，两路索引使用相同 chunk ID。
3. 可查看稠密、稀疏、RRF 和重排序候选，证明混合链路真实生效。
4. 普通问答与加工指令各完成至少 1 个真实样例，引用可回到实际 PDF 页和原文。
5. 无答案问题不生成虚假引用或无依据关键参数，输出保留人工审核提示。
6. 解析、分块、RRF、上下文预算和引用校验有自动化测试，至少 1 条真实 API 集成用例通过。
7. 6—10 道冒烟题保存输入、原始输出、配置和人工核查结论。

### I2—I3：完整产品与多文档闭环

- I2 至少使用 3 份不同 PDF 验证统一检索、版本一致性和文档生命周期；同一文件重复上传、异常 PDF、失败重试、重启恢复、重建与删除都有明确结果。
- I2 完成不少于 30 题的测试题集 v1，覆盖期望要点、必须引用页、多轮和无答案题。
- I3 完成服务端权限、会话归属、多轮改写、SSE 断连恢复、幂等提交、引用抽屉和文档筛选。
- I3 至少通过 1 条覆盖登录、上传、提问、追问、引用定位和退出登录的 E2E 用例。

### I4—I6：首版质量门槛

- 固定文档哈希、索引版本、测试集、模型和检索配置，保存原始回答，不在评分前手工修改。
- 完成 A 仅稠密、B 仅 BM25、C 混合无重排序、D 混合加重排序的对比；没有相关标注时不伪造检索指标。
- 引用可核查率达到 100%，无依据关键参数率为 0；有效回答率目标不低于 80%，未达标须记录阻断原因和处置结论。
- 完成模型超时、Qdrant 不可用、worker 崩溃、越权、提示注入、恶意文件和备份恢复测试。
- 100 页以内文本型 PDF 可正常入库；检索 P95 目标不高于 3 秒，未达建议目标时记录实测环境和差距。
- I6 结束时，核心 P0 应具备发布条件。未达标项进入 I7 优先处理，可选增强不得挤占修复时间。

### I10—I12：中期后的优化与验收预演

- 优化必须来源于中期反馈、失败样本或可复现指标，记录优化前后结果，不凭主观感觉调参。
- 若核心功能仍有缺口，I10—I11 先补齐核心范围；若已达标，则只做解析、检索、交互、诊断和维护性的小步改进。
- I12 按最终交付方式执行干净环境部署和全量验收预演，主要功能原则上冻结。
- OCR、复杂表格和其他扩展必须单独评审，不得影响已稳定的 P0 链路。

### I13—I16：微调与最终交付

- 只接受低风险、可回归验证的改进，不再进行无评估依据的大规模架构调整。
- 最终回归覆盖所有 P0、核心 P1、E2E、多文档人工评估、安全异常、性能和备份恢复。
- 使用至少 3 份 PDF 稳定演示上传、索引、问答、加工指令、多轮追问、引用查看和评估导出。
- 交付包括正式版本、安装配置说明、测试与评估记录、演示材料、已知限制和版本说明。
- 若 I12 已满足全部交付条件，可提前形成正式版本；I13—I16 保持微调、复验和材料完善，不人为制造新需求。

## 6. 中期报告安排

### 时间窗口

中期报告在下学期开学后的第 1—3 周完成，暂按 I8—I9 组织材料。校历公布后补充准确提交日；若开学日期变化，优先保证“第三周结束前定稿”，而不是机械沿用表内日期。

### 第 1—3 周任务

| 时间 | 任务 | 输出 |
| --- | --- | --- |
| 第 1 周 | 核对计划与实际进度，冻结中期演示版本，整理需求和设计变更 | 进度对照、需求追踪表、版本与变更清单 |
| 第 2 周 | 汇总软件测试、检索对比和人工评估，执行完整演示并收集问题 | 测试/评估摘要、演示记录、问题清单、报告初稿 |
| 第 3 周 | 完成报告定稿和汇报材料，复盘偏差并调整后续双周迭代 | 中期报告、汇报材料、后半程计划与风险更新 |

### 中期报告内容

1. 项目背景、目标、范围及核心安全边界。
2. 需求、总体架构、关键数据模型和 RAG 链路说明。
3. 已完成需求及证据，不用主观百分比代替可验收功能清单。
4. 至少 3 份真实 PDF 的端到端演示结果。
5. 自动化测试、A/B/C/D 检索对比和人工评估的阶段结果。
6. 与原计划的偏差、原因、已解决问题和当前风险。
7. 后续优化、验收和最终交付安排。

**中期最低可演示基线**：多文档入库与管理、混合检索、普通问答和加工指令、引用溯源、多轮会话及固定题集评估。若个别 P1 尚未完成，应明确说明，不影响对真实完成情况的报告。

## 8. 弹性调整机制

### 进度提前

- 核心 P0 提前完成时，提前进入评估和加固，不等待下一轮日期。
- 全部发布条件提前满足时，可提前冻结正式版本。
- 后续迭代仅用于高价值微调、扩充回归样本、改善易用性、完善文档和准备验收；每项改进仍须有假设、验证结果和回归证据。

### 进度落后或难度超预期

- 先保障 P0 的端到端正确性、引用可靠性和安全边界，再考虑 P1 与可选增强。
- 连续两轮未解决的核心风险必须升级处理，重新评估技术方案或范围，并同步中期/最终报告。
- 可压缩界面美化、低频管理和可选解析增强，不得省略真实混合检索、引用核查、权限、评估和恢复等核心验收。
- 中期后仍有 P0 缺口时，I10—I11 优先补核心，I12 重新进行验收预演；不得把缺口改名为“优化项”。

### 变更记录

每次调整记录变更项、原因、影响需求、前后验证结果和新的验收时间。双周复盘更新本计划及需求追踪，不以增加文档代替解决实际问题。

## 9. 工作分解与并行规则

| 工作流 | 主要任务 | 关键依赖 | 主责迭代 |
| --- | --- | --- | --- |
| 前端 | 最小问答、文档管理、会话与引用、评估页面 | API 首版约定 | I1—I4，后续按反馈微调 |
| 后端基础 | 配置、迁移、文件与任务、认证、会话、错误规范 | I1 项目骨架与配置决策 | I1—I3、I6 |
| RAG | 解析分块、双路索引、融合、重排序、生成与引用 | 真实 PDF、模型服务、索引组织决策 | I1—I5，后续按证据优化 |
| 质量 | 单元/集成/E2E、题集、人工评估、性能安全 | 各轮可运行产物与固定数据版本 | 全程，I4—I6、I12、I15 集中 |
| 运维 | Compose、日志、备份、监控、部署与恢复 | 数据目录、模型配置和基础设施 | I1、I6、I14—I16 |

并行规则：

1. API 首版冻结后，前端可用固定 mock 并行开发；每轮准出前必须切换真实 API。
2. 文档链路未完成时，可用页文本样本开发检索单元测试；联调和验收必须使用真实 PDF 与真实索引。
3. 测试题和页级标注从 I1 开始准备，不得到最后只选择有利样本。
4. 人工评估从 I1 冒烟题开始，I4 建立正式基线；严重问题立即进入当前或下一轮最高优先级。
5. 数据库迁移、索引版本和 API 变更先由后端与 RAG 共同评审，再同步前端和测试。

## 10. 风险清单

| 风险 | 影响 | 早期信号 | 应对与责任角色 |
| --- | --- | --- | --- |
| 样例 PDF、模板或模型配置未按时确认 | I1 无法真实验收 | 启动后仍只有 mock 或演示文本 | 后端/RAG 立即列出阻塞与所需决策；保留真实验收门槛 |
| PDF 扫描件或复杂表格导致解析差 | 检索知识缺失 | 页文本为空、参数错行 | RAG 预检并明确限制；可选 OCR/表格扩展不得挤占核心范围 |
| 多文档索引版本或 BM25 统计口径不一致 | 排名失真、删除后仍命中 | 两路来自不同版本，多文档结果异常 | RAG/后端在 I1 决策，I2 用版本切换和删除测试验证 |
| 中文术语/型号检索差 | 关键资料未召回 | 精确查询失败 | RAG 检查分词、型号和单位保留规则，用固定题集比较 |
| 分块破坏工序上下文 | 答案片面或引用错位 | 表头与参数分离 | RAG 使用结构感知分块、相邻块合并和页级评估 |
| 重排序阈值误杀 | 有答案却拒答 | 候选相关但被过滤 | RAG 在 I4—I5 校准阈值，保留诊断并按题型验证 |
| 大模型编造参数或引用 | 生产安全风险 | 无来源数值、非法编号 | RAG/后端执行强约束、结构校验、白名单和拒答；阻断发布 |
| 多轮历史污染检索 | 回答错对象 | 换话题仍检索旧实体 | 后端/RAG 独立改写、限制历史并测试会话隔离 |
| SQLite 并发限制 | 写入失败或任务卡死 | 数据库锁定 | 后端保持单 worker、短事务和 WAL；扩展时先迁移 PostgreSQL |
| 模型 API 不稳定或成本高 | 响应失败、成本超预算 | 超时、限流、token 增长 | 后端/RAG 设置超时、有界重试、上下文预算和用量统计 |
| 文档含提示注入 | 指令被覆盖或泄露 | 回答泄露系统提示或执行文档指令 | 后端/RAG 隔离上下文与指令，密钥不进入提示 |
| 评估样本过少或标注偏差 | 指标失真 | 只测简单事实题 | 测试/评估在 I2 覆盖多文档多题型，关键样本复核 |
| 涉密资料外发 | 合规风险 | 使用外部模型处理未批准文档 | 系统管理员落实数据分级、脱敏、内网模型或审批 |
| 寒假和中期节点影响连续开发 | 联调与报告准备不足 | I7 前演示不稳定、材料分散 | 提前冻结可演示版本，I7 保持弹性工作量，I8 起集中整理材料 |
| 长周期导致范围持续扩张 | 核心质量下降、后期返工 | 每轮增加与评估无关的新功能 | 以 P0 和证据为导向，I12 后主要功能冻结，后续只微调完善 |

## 11. 质量完成定义（Definition of Done）

一个功能只有同时满足以下条件才算完成：

- 代码通过项目规定的格式检查、静态检查和相关自动化测试。
- 正常路径及约定异常路径均验证；最终端到端验收不使用模型 mock。
- 权限、日志、配置和错误响应符合文档，不暴露堆栈、密钥和内部路径。
- 数据库变更提供迁移，索引变更说明版本与重建方式。
- API 或业务规则变化已同步文档和需求追踪表。
- 无硬编码密钥、绝对本机路径或未经确认的依赖。
- 用户可观察到明确结果，不仅后台打印成功日志。
- 验收证据已保存，严重失败已修复或有明确的发布阻断结论。
