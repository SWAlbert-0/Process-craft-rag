# 协作与提交规范

> 基线日期：2026-11-22。本文件适用于所有人工开发者和 AI 辅助开发者。使用 AI 时，必须先把下方提示词放入该次开发任务的上下文中；不能用“AI 生成了代码”为理由绕过评审、测试或 Git 规范。

## AI 开发提示词（必须复制到任务开头）

```text
你正在参与 Process-craft-rag 项目开发。开始读取、修改或提交代码前，必须阅读并遵守：
1. docs/开发文档/协作与提交规范.md；
2. docs/开发文档/开发计划.md；
3. 与本次改动相关的需求、架构、接口、检索、测试和部署文档。

工作约束：
- 先检查 git status，保留用户已有改动；不得覆盖、删除或提交与本任务无关的文件。
- 未经用户明确要求，不得执行 git commit、git push、合并、变基、标签或发布操作。
- 不得直接提交或推送 main，不得绕过 GitHub 分支保护。所有合并必须通过 PR。
- 分支使用 <类型>/<迭代>-<简短英文描述>，提交使用 <类型>(<迭代>): <中文说明>，PR 使用 [I<迭代号>] <标题>。
- 默认通过短生命周期功能分支和 Squash Merge 合并；不得擅自强制推送共享分支。
- 不得使用 git add . 后不加检查地提交。必须明确暂存路径，并检查 git diff --cached、工作区状态和敏感信息。
- 严禁提交 .env、真实 API Key、Workspace ID、data/、models/、模型权重、日志、虚拟环境、node_modules 或构建产物。
- 不得把真实密钥写入提示词回复、代码、测试、截图、日志、PR、Issue 或文档；连接测试失败时只记录脱敏原因。
- 修改需求、API、配置、数据模型或核心链路时，必须同步对应设计文档和根 README；迭代完成后更新验收报告与需求追踪。
- 必须运行与改动相关的标准检查。没有执行、被跳过或因缺少外部服务而未验证的项目，必须明确说明，不能声称通过。
- 不得伪造测试、真实模型调用、人工评分、提交哈希、指标或验收证据；模型 mock 不能代替最终真实 RAG 验收。
- 新发现的无关问题只记录，不顺手扩大修改范围；范围变化必须在 PR 和开发计划中说明。
- 完成后报告：修改内容、测试命令与结果、未验证项、已知风险、当前 Git 状态。除非用户明确要求，否则保持未提交状态。

本次任务仍须以用户在当前会话中的明确要求为准；本提示词不授权自动提交、推送或发布。
```

## 1. 基本原则

1. `main` 只接受通过 PR 的已验证改动，不接受直接推送，即使当前账号拥有绕过权限也不得绕过。
2. 一个分支只解决一个明确交付物；优先小步提交和小型 PR，不把多个迭代或无关重构混在一个 PR 中。
3. 代码、测试、文档和验收证据必须对应。不得用“代码已写”代替功能验证。
4. 保留他人未提交改动；发现无关问题时先记录，未经要求不扩大范围。
5. AI 生成内容与人工编写内容执行相同标准，作者对提交内容、依赖、安全和验证结果负责。

## 2. 分支命名

格式：

```text
<类型>/<迭代>-<简短英文描述>
```

常用类型：`feat`、`fix`、`docs`、`test`、`refactor`、`chore`。

示例：

```text
feat/i1-core-rag
feat/i2-document-management
fix/i2-index-consistency
docs/i2-evaluation-dataset
test/i2-snapshot-recovery
```

规则：

- 使用小写英文和连字符，不使用含混的 `dev`、`temp`、`final-new` 等长期分支名。
- 从最新 `main` 创建短生命周期分支，合并后删除本地和远程功能分支。
- 不为每个开发者建立长期个人分支；协作者通过独立任务分支协作。
- 已在共享分支上的工作不得擅自变基或强制推送。

## 3. 提交命名与拆分

格式：

```text
<类型>(<迭代>): <中文说明>
```

示例：

```text
feat(i1): 实现单文档 RAG 与最小工作台
fix(i2): 修复快照切换后的文档状态
docs(i1): 补充验收证据与启动说明
test(i2): 覆盖失败任务恢复与重试
```

要求：

- 一个提交只表达一类逻辑变化；代码与纯文档可以分开提交。
- 提交信息说明结果，不写 `update`、`fix bug` 等无法追踪的文本。
- 不提交无法通过基本检查的半成品；确需保存中间进度时只留在个人功能分支，并在 PR 前整理。
- 不在提交信息中写密钥、内部路径、未经授权的数据或冗长 AI 生成记录。
- 不必为了拆分提交而拆分相互依赖、单独无法运行的代码。

## 4. 提交前检查

### 4.1 明确暂存范围

优先明确路径暂存，不直接对未检查的工作区执行 `git add .`：

```bash
git status --short
git add .gitignore .env.example compose.yaml backend frontend
git add README.md docs
git status --short
git diff --cached --stat
git diff --cached --check
git diff --cached
```

上述仅为路径示例，实际提交必须排除与本任务无关的文件。`docs` 中的外部数据还要遵守各自许可和既有忽略规则。

### 4.2 禁止进入仓库的内容

- `.env`、真实 API Key、Workspace ID 和其他凭据。
- `data/`、`backups/`、`logs/` 中的运行时数据、数据库、原文副本、索引和运行时密钥文件。
- `models/`、模型权重及 Hugging Face 缓存。大模型文件通过可信来源下载，不使用普通 Git 提交。
- `.venv/`、`node_modules/`、`dist/`、测试缓存和临时调试脚本。
- 许可证不允许再分发或尚未确认许可的资料。

若 `models/` 尚未被 `.gitignore` 排除，应先补充忽略规则，再暂存。不得通过删除用户本地文件来“清理”提交范围。

### 4.3 标准验证

按改动范围执行，不以导入或编译代替真实功能测试：

```bash
cd backend
uv run ruff check app tests scripts migrations
uv run pytest -q
RUN_QDRANT_TESTS=1 uv run pytest -q  # 需要 Qdrant 时执行

cd ../frontend
npm run build
npm audit

cd ..
docker compose config --quiet
```

核心 RAG、引用、加工指令或入库链路变化还必须使用真实文本型 PDF、真实 Qdrant 和真实模型执行端到端验证，并保存非敏感证据。外部服务不可用或密钥失效时，如实记录阻断，不能用 mock 结果冒充真实验收。

提交前最后确认：

```bash
git status --short
git diff --cached --check
```

## 5. 文档同步规则

| 改动类型 | 必须同步的文档 |
| --- | --- |
| 需求、范围或迭代计划 | 需求分析、PRD、开发计划、需求追踪 |
| API、错误码或数据结构 | 数据与接口设计、前端调用、根 README（如影响使用） |
| 模型、环境变量或设置页 | 部署运维与安全设计、`.env.example`、根 README |
| 检索、分块、引用或生成规则 | 检索与生成详细设计、相关 UML、测试方案 |
| 部署、启动或依赖 | 根 README、部署设计、Compose/锁文件 |
| 迭代验收 | `docs/评估记录/I<迭代号>/验收报告.md`、原始证据和开发计划 |
| 协作或合并流程 | 本文件及文档导航 |

`docs/` 只维护 `docs/README.md` 这一份 README。新的专项说明应使用含义明确的独立文件名，并加入导航。

## 6. PR 规范

标题：

```text
[I<迭代号>] <可验收的交付物>
```

本次 I1 示例：

```text
[I1] 单文档 RAG 核心链路与最小工作台
```

PR 正文至少包含：

```markdown
## 目标与范围
- 实现了什么，明确哪些内容不在本 PR 内。

## 主要改动
- 按用户能力或子系统说明，不只罗列文件名。

## 验证
- 列出实际执行的命令、测试数量和结果。
- 真实模型、Qdrant、浏览器或 Docker 验证分别说明。

## 质量与风险
- 如实列出基线、失败样本、外部服务阻断和后续处理。
- 不把开发核查写成独立人工评审。

## 文档与兼容性
- 列出文档更新、配置/数据库迁移和索引重建要求。

## 安全
- 确认无密钥、未授权数据、模型权重和无关文件。
```

团队协作时应经过非作者评审；个人项目可以使用自审清单，但不得伪造他人评审或批准。

## 7. 合并策略

1. 默认使用 **Squash Merge**，使 `main` 中每个 PR 保留一个清晰、可回退的提交。
2. Squash 后的标题使用 PR 标题或标准提交格式，正文保留主要改动和验证摘要，删除重复的中间提交记录。
3. 合并前必须同步最新 `main`、解决冲突并重新执行受影响检查。
4. 检查未通过、真实验收被阻断或包含未审查敏感文件时不得合并。
5. 不使用直接推送、强制推送或绕过分支保护来完成合并。
6. 合并后删除功能分支；本地切回 `main` 并快进更新：

```bash
git switch main
git pull --ff-only origin main
```

只有确需保留完整多提交历史、且项目评审明确同意时，才使用 merge commit；不要在同类 PR 中随机切换合并策略。

## 8. 迭代标签与发布

迭代验收合并后使用：

```text
i1-v1
i2-v1
i3-v1
```

标签指向 `main` 上对应的合并提交，名称表示迭代检查点，不代表生产发布。创建和推送标签必须由用户明确要求或在已批准的验收流程中执行。

正式版本使用语义化版本：

- 首版：`v0.1.0`
- 发布候选：`v0.1.0-rc.1`
- 最终正式版：根据验收结论决定是否使用 `v1.0.0`

验收报告引用合并提交或迭代标签，不在同一个提交中写入其自身哈希。GitHub Release 可作为补充，不能替代仓库内验收报告。

## 9. I1 首次上传约定

I1 推荐分支与提交：

```text
feat/i1-core-rag
  ├─ feat(i1): 实现单文档 RAG 与最小工作台
  └─ docs(i1): 补充验收证据与启动说明
```

PR 标题：

```text
[I1] 单文档 RAG 核心链路与最小工作台
```

PR 使用 Squash Merge 后，在 `main` 上标记 `i1-v1`。上传前必须排除本地 `models/` 模型文件，并将验收报告中的版本描述改为引用合并提交或 `i1-v1`，不再保留“尚未 Git 归档”的待办文字。

## 10. AI 完成回复格式

AI 完成任务后必须简洁报告：

```text
已完成：...
验证：实际命令及结果；未执行或跳过的项目单独列出。
已知问题：...
Git：分支、未提交/已提交状态；未经要求不得声称已推送。
```

若用户要求“先不要上传”，AI 只能检查和提出流程，不能创建提交、推送分支、创建 PR、打标签或发布。
