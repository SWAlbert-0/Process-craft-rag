## 1. 项目定位与需求基线

本项目面向企业工艺知识场景，基于开源向量数据库与大模型 API，构建轻量级检索增强生成（RAG）系统。系统将 PDF 工艺文档解析、分块并向量化，通过稠密与稀疏混合召回、重排序和大模型生成，输出带引用来源的零件加工指令，并支持多轮对话。

### 1.1 七项需求基线

1. 支持 PDF 工艺文档解析。
2. 支持文档分块、向量化及开源向量数据库存储。
3. 同时提供稠密语义召回与稀疏关键词召回。
4. 对混合召回结果重排序后再生成。
5. 支持多轮对话。
6. 回答和加工指令支持引用溯源。
7. 使用多份文档和人工评估测试回答准确性。

### 1.2 P0 功能摘要

系统用户包括工艺人员、知识库管理员和评估人员。P0 功能包括：

1. PDF 上传、校验、异步解析、分块、索引、状态查询、失败重试与删除。
2. 稠密与 BM25 双路召回、RRF 融合、重排序和上下文预算控制。
3. 知识问答、加工指令草案、多轮问题改写及历史隔离。
4. 文档名、页码和原文片段组成的引用快照及原文定位。
5. 多文档测试集、检索诊断、人工评分和结果导出。

核心约束：仅 `ready` 文档参与检索；引用必须来自实际注入的上下文；缺失材料、公差或设备信息时标为“待确认”；输出仅供工艺人员审核，不直接生成机床控制指令。

### 1.3 默认技术边界

- 首个版本（MVP）面向单机或小团队内网使用，采用单租户、少量角色的轻量部署。
- 默认使用 FastAPI、Vue 3、Qdrant、SQLite、PyMuPDF，以及兼容 OpenAI Chat Completions 的大模型 API。
- LLM、嵌入和重排序模型优先使用外部 API，也可接入 Ollama、Hugging Face 等本地模型提供的兼容 API；通过统一配置替换，不改变业务流程。
- 当前项目样例允许发送至所选外部模型服务；后续新增资料仍需单独确认外发权限。
- I1 加工指令先采用 [PRD 默认模板](./开发文档/02-产品需求说明.md#5-加工指令输出约定)，所有输出仍须由工艺人员审核。
- 稀疏召回默认使用本地 BM25。
- 原始文件默认保存在受控本地目录；不将公共云存储作为 MVP 的必要依赖。
- 系统输出仅作为工艺辅助建议，不直接下发机床或替代工艺人员审核。

## 3. 调研与概要设计

### 3.1 工艺知识数字化需求

工艺规划连接设计信息与制造执行，涉及加工方法、设备、工装、参数、测量及质量要求。NISTIR 7734 通过活动模型分析加工与测量工艺规划中的数据交换，说明工艺知识具有多环节、多来源和强上下文特征[1]。国内《“十四五”智能制造发展规划》强调以工艺、装备为核心，以数据为基础，构建知识驱动的智能制造系统[2]。因此，本项目不把目标简化为通用聊天，而是围绕企业文档建立可检索、可核查的工艺知识服务。

### 3.2 RAG 技术进展

Lewis 等提出的 RAG 将参数化语言模型与非参数化检索记忆结合，为知识更新和来源追踪提供了基础路径[3]。后续综述将 RAG 归纳为由朴素检索—生成向高级检索优化、模块化编排演进，并强调检索、生成与评估的协同[4]。这说明工程重点不只是接入大模型 API，还包括文档处理、检索质量、上下文组织和可复现评估。

稠密检索利用向量语义匹配提高同义表达和跨语言查询的召回能力[5]；BM25 保留术语、型号、数值等词法匹配优势[6]。RRF 按不同检索结果中的排名进行融合，避免直接比较异构分数[7]。重排序进一步对较小候选集进行精细相关性判断，但会增加时延，需通过候选规模和阈值控制成本。

### 3.3 现有方案不足与项目切入点

通用大模型无法自动获得企业内部工艺知识，且回答来源难核查；单一向量检索容易遗漏精确术语或型号；只返回检索片段又不能形成连续问答与结构化加工指令。项目采用“PDF 页级解析—稠密与稀疏混合召回—RRF 融合—重排序—受控生成—引用校验”的完整链路，以人工审核和证据不足拒答作为工艺安全边界。

### 3.4 概要设计

系统采用前后端分离的单体后端和单后台 Worker，避免在轻量项目中引入微服务复杂度。表现层使用 Vue 3；服务层使用 FastAPI；SQLite 保存权威元数据；Qdrant 保存向量索引；BM25 保存词法索引；本地受控目录保存 PDF；大模型通过服务端 API 调用。

离线索引与在线问答解耦。离线索引在暂存版本中完成解析、嵌入和两路索引构建，通过一致性校验后原子发布。在线问答固定活动版本，完成问题改写、双路召回、融合、重排序、受控生成和引用快照保存。

## 5. 可行性验证计划

采用迭代式开发：先打通单文档端到端链路，再扩展多文档与评估。准备不少于 3 份授权文本型 PDF 和不少于 30 道测试题，对比仅稠密、仅 BM25、混合召回和混合召回加重排序四种配置。软件测试与人工评估分离，人工从正确性、完整性、引用正确性、表达和多轮一致性按 0–2 分评分；建议目标为有效回答率不低于 80%、引用可核查率 100%、无依据关键参数率 0。

具体双周日期、交付物和中期报告安排以[开发计划与风险](./开发文档/开发计划.md)为准。

### 6.1 结论与目录

实际保留的 6 份 PDF 均可作为项目数据集，但用途不同：

- **第一次迭代单文档**：A4 NIST AMS 400-1。
- **快速冒烟测试**：A6 NISTIR 8127；需要完整流程时仍使用 A4。
- **多文档核心评估集**：A1 + A2 + A4，覆盖加工操作、质量/SPC、机内测量三个内容方向。
- **鲁棒性与扩展评估**：A5 用于图示和文本稀疏页面，A7 用于长文档及设计—制造综合内容。
- **不混入默认核心基线**：A5 的图示页较多，A7 篇幅长且含非商业许可限制，相关结果应单独报告。

这些资料可以支撑英文 PDF 的解析、混合检索、引用溯源和多文档问答开发，但不足以单独完成最终验收：当前没有独立安全规范、独立材料手册、中文工艺 PDF 或真实企业工艺规程。

### 6.4 建议的数据集划分

#### `i1_single`：第一次迭代

- **文件**：仅 A4。
- **原因**：69 页、全部页面有文本，内容同时包含定义、活动和步骤，便于控制首次联调规模。
- **验收重点**：上传至 `ready`、两路索引 chunk ID 一致、四阶段检索诊断、普通问答、结构化草案、引用核查和无答案拒答。
- **限制**：I1 通过只说明单文档技术链路成立，不代表多文档或完整工艺生成质量达标。

#### `parser_smoke`：快速回归

- **文件**：A6。
- **原因**：32 页且全部有文本，适合每次解析器、分块或索引改动后的快速回归。
- **建议检查**：页数、文本非空、标题路径、确定性 chunk ID、页码引用和少量固定问题。

#### `core_eval_v1`：多文档核心评估

- **文件**：A1 + A2 + A4。
- **选择理由**：满足项目“至少 3 份内容不同 PDF”的演示要求，同时覆盖加工、测量和质量控制。
- **建议首版 30 题**：A1 12 题、A4 10 题、A2 8 题。
- **题型要求**：单文档事实、精确术语/数值、跨页流程、多文档综合和无答案问题均应覆盖；多文档题只在一个主问题 ID 下计数，避免重复。
- **标注要求**：每题保存期望要点、必须引用页、是否应拒答和关联文档；检索指标另需相关页/块列表。

A7 不进入默认 `core_eval_v1`，以保持核心基线许可一致并控制文档规模。A5、A6 的结果作为专项补充，不用于冲淡核心集失败样本。

#### `robustness_ext`：扩展与压力测试

- **A5**：测试文本稀疏页、模型图、跨页上下文和引用稳定性。
- **A7**：测试 355 页长文档、跨章节综合和索引容量；仅在符合 CC BY-NC 4.0 的教学/研究场景使用。
- **报告方式**：与核心集分开列出解析成功率、耗时、失败样本和人工评分，不与 `core_eval_v1` 平均成一个总指标。

### 6.7 后续必须补充的数据

## 7. 待确认事项

以下事项不阻塞 I1 启动，在对应功能、模型切换或阶段验收前形成结论：

- Kimi、GLM、OpenAI 备选 LLM 的具体密钥、费用和真实 API 连通性；只有实际切换前才需要完成对应验证。
- 替换嵌入或重排序服务时，重新核验接口、维度、费用、检索效果和阈值；当前百炼默认模型的最小真实调用已通过。
- 面向真实企业资料的领域加工指令模板及必备字段，后续由工艺人员提供并确认；I1 已确定使用 PRD 默认模板。
- 用户规模和部署机器配置，以确定并发及本地模型的资源需求。
- 人工评估集规模、评估人员和最终通过阈值。
