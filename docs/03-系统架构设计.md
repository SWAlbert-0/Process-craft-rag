# 系统架构设计

## 1. 设计目标

架构优先满足轻量部署、核心链路完整和模块可替换。MVP 采用前后端分离的单体后端、单后台工作进程和本地基础设施，不提前引入微服务。文档处理与在线问答解耦，检索各阶段可独立观测和测试。

## 2. 技术选型

| 层次 | 默认方案 | 选择理由与边界 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Element Plus | 适合管理与会话界面，生态成熟 |
| 后端 | Python、FastAPI、Pydantic | 便于复用文档和模型生态，自动校验 API |
| 元数据 | SQLite（SQLAlchemy） | 零额外服务，适合单实例 MVP |
| 向量数据库 | Qdrant（开源） | 支持向量检索、过滤、集合别名和持久化 |
| 稀疏检索 | BM25，本地持久化索引 | 轻量，适合术语和型号精确匹配；规模扩大可换 OpenSearch |
| PDF 解析 | PyMuPDF；必要时扩展 pdfplumber | 保留页级文本，满足文本型 PDF |
| 嵌入模型 | 可配置中文/多语向量模型 | 通过统一接口调用本地或远程实现 |
| 重排序 | 可配置 Cross-Encoder，如 BGE Reranker 系列 | 与生成模型解耦，具体型号经基准测试确定 |
| 大模型 | OpenAI 兼容 Chat Completions API | 服务端统一鉴权，供应商可替换 |
| 文件存储 | 受控本地目录 | MVP 简单可靠，后续可换 S3 兼容对象存储 |
| 部署 | Docker Compose；开发环境可本机运行 | 统一管理 API、前端、Qdrant 和 worker |

具体依赖版本在初始化项目时锁定，不在设计阶段虚构版本号。

## 3. 总体架构

```text
浏览器（Vue 3）
  ├─ 会话、消息、引用展示
  └─ 文档与评估管理
          │ HTTPS / REST / SSE
          ▼
FastAPI 单体后端
  ├─ 身份认证与权限
  ├─ 文档 API ───────────────┐
  ├─ 会话与消息 API          │
  ├─ RAG 编排                │
  │   ├─ 查询改写            │
  │   ├─ 稠密检索 ──► Qdrant │
  │   ├─ 稀疏检索 ──► BM25   │
  │   ├─ RRF 融合            │
  │   ├─ 重排序              │
  │   ├─ 上下文构建          │
  │   └─ LLM API / 引用校验  │
  └─ 评估与审计              │
          │                  ▼
   SQLite 元数据        持久任务表 + Worker
          │             ├─ 文件校验与解析
   本地 PDF 存储 ◄──────┤─ 清洗、分块、嵌入
                        └─ Qdrant / BM25 索引发布
```

## 4. 模块职责

### 4.1 前端

- 只调用后端 API，不持有模型或向量库密钥。
- 文档状态轮询采用指数退避，页面不可见时暂停。
- 会话流式响应使用 SSE；消息 ID 和请求 ID 用于避免重复渲染。
- 引用使用服务端结构化数据，不解析模型文本猜测来源。

### 4.2 API 与鉴权

- 提供 REST 资源接口和 SSE 生成接口。
- 密码使用可靠算法哈希，登录后使用 HttpOnly、SameSite Cookie；具体会话机制实现时确定。
- 所有文档与会话查询都执行权限和归属过滤。
- 请求层负责输入校验、错误转换和请求 ID，不包含检索业务细节。

### 4.3 文档处理 Worker

- 使用 SQLite 持久任务表记录任务及租约，单 worker 从队列取任务。
- 任务阶段：文件检查、页文本提取、清洗分块、向量计算、索引暂存、版本发布。
- 每阶段完成后提交检查点；崩溃重试利用确定性 ID 和幂等写入。
- MVP 仅运行一个 worker，避免 SQLite 写锁竞争；扩展多 worker 前先迁移 PostgreSQL 和独立队列。

### 4.4 RAG 编排

同步组合独立服务接口：`QueryRewriter`、`DenseRetriever`、`SparseRetriever`、`FusionService`、`Reranker`、`ContextBuilder`、`LLMClient`、`CitationService`。每个阶段记录输入摘要、输出数量、耗时和配置版本，以便测试混合召回真实生效。

## 5. 核心处理链路

### 5.1 离线索引

```text
PDF → 文件哈希/安全校验 → 按页解析 → 文本清洗
    → 结构感知分块 → chunk 元数据入库
    → 批量嵌入 → 写入暂存 Qdrant collection
    → 构建暂存 BM25 索引 → 一致性校验
    → 原子发布索引版本 → 文档 ready
```

关键规则：

- 分块 ID 由文档内容版本和块序号确定，重复执行不会产生重复知识。
- 页码、标题路径、字符偏移和原文随块保存。
- 新文档所有索引均通过一致性检查后才进入 `ready`。
- 重建时创建新版本，旧版本继续服务；发布通过元数据中的活动版本指针完成，随后异步清理旧版本。
- Qdrant collection 可按索引版本命名，避免原地更新造成一半新一半旧。
- BM25 使用相同活动版本；检索开始时固定版本，保证一次请求的两路召回来自一致快照。

### 5.2 在线问答

```text
问题 + 会话历史 + 文档过滤
  → 独立检索问题
  → 并行为稠密 top-k 与稀疏 top-k
  → RRF 融合去重
  → 重排序 top-n
  → 阈值过滤 + 去重 + 上下文预算控制
  → 提示词 + 允许引用编号
  → 大模型回答
  → 引用合法性与结构校验
  → 保存消息和引用快照 → SSE/JSON 返回
```

- 稠密和稀疏召回都必需，任一路不可用时记录明确错误；是否允许降级只能由配置决定，且响应必须标记降级，不能宣称完整混合检索。
- 证据不足由“无候选、低于阈值、上下文校验失败”等条件触发。
- 模型输出引用编号须属于允许集合，非法编号删除并触发结构校验/重试；不得保留伪引用。

## 6. 数据流与一致性

- SQLite 是文档、版本和任务状态的权威来源；Qdrant 与 BM25 是可重建索引。
- 文档状态和活动索引版本必须一致，检索器只读取 `ready` 文档的活动版本。
- 文件和索引清理采用先下线、后删除的顺序。
- 启动时执行一致性检查：缺失文件、无活动版本、孤立任务和过期租约。
- 嵌入模型或分块策略变化必须创建新索引版本，禁止复用旧向量。

## 7. 配置设计

配置通过环境变量和本地非敏感配置文件组合，密钥只从环境变量或密钥管理工具读取。

主要配置组：

- 服务：监听地址、允许来源、会话有效期、上传限制。
- 存储：数据目录、SQLite URL、Qdrant URL、索引根目录。
- 模型：LLM Base URL、API Key、模型名、超时、重试、最大输出 token。
- 嵌入：模型名、维度、批大小、归一化方式。
- 检索：两路 top-k、RRF 常数、重排序 top-n、相关性阈值、上下文预算。
- 分块：目标长度、重叠长度、最小块长度和策略版本。

## 8. 性能与容量策略

- PDF 页文本解析和嵌入批处理，避免一次性加载全部向量。
- 检索两路并行，模型客户端设置连接池、超时和有限重试。
- 上下文按 token 预算截断，而不是简单按字符无限拼接。
- SQLite 开启 WAL；写操作短事务，嵌入等长耗时操作在事务外执行。
- 首版不承诺高并发；通过压力测试得到容量基线。
- 大规模扩展顺序：PostgreSQL/独立队列 → 对象存储 → 独立稀疏检索服务 → 多实例 API。

## 9. 故障处理

| 故障 | 处理方式 |
| --- | --- |
| 上传中断 | 临时文件不入库；定时清理过期临时文件 |
| Worker 崩溃 | 任务租约过期后重试，超过上限标记失败 |
| Qdrant 写入部分成功 | 暂存版本不发布，按确定性 ID 重试或整体重建 |
| BM25 构建失败 | 不发布新版本，旧版本继续服务 |
| LLM 超时/限流 | 有界指数退避；最终失败保留可重试消息 |
| 模型输出格式错误 | 最多一次修复重试；仍失败则返回明确错误 |
| 索引与元数据不一致 | 文档下线并报警，不返回不可靠结果 |

## 10. 架构决策

1. **单体优先**：当前规模无需微服务，降低部署和联调成本。
2. **Qdrant + BM25**：同时满足开源向量数据库与轻量稀疏召回，不把向量库当作唯一检索手段。
3. **服务端 RAG 编排**：保护密钥并保证评估、日志和引用规则一致。
4. **版本化索引**：保证重建、删除和多路检索的一致性。
5. **引用快照**：回答可复查，即使后续文档发生变化也不篡改历史依据。
6. **人机协同**：仅生成工艺草案，不承担自动生产控制责任。
